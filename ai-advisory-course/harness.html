Harness Field Manual

The model is the horse. Everything that turns its strength into useful work, the reins, the wagon, the map, and the rules of the road, is the harness. This is a guide to that second part, the one you will actually design for clients.

I

Anatomy of a harness

A language model does exactly one thing. It takes text in and writes text out. It can't open a file, search a database, or remember yesterday. It can only write.

A harness is all the software around the model that turns that one ability into work. Every AI product you have used, from ChatGPT to Harvey to Claude Code, is a model plus a harness. When two products use the same model and one is far better, the harness is the difference.

Here is the same model inside two different harnesses. On the left, a chat window. On the right, an agent harness like Claude Code. The model hasn't changed. What changed is what the harness lets it reach and how many times it gets to try.

For a client, the question is rarely "which model?" It's "how much of the right wagon do we build, and what are we willing to let it reach?"

III

The loop, one step at a time

This is the mechanism under every agent. Step through a real-shaped task: "Which of these ten agreements has a non-compete longer than 12 months?" Watch the context window on the right. It's the model's entire working memory, and the harness rebuilds it on every call.

CONTEXT WINDOW0 tokens

Notice the last number. The API is stateless, so every call resends the whole window. Twelve calls over a growing window billed about 359,000 input tokens, nearly six times the 63,000 the window ends at. Long contexts also dilute attention: the model gets worse at finding the one clause that matters. Both are harness problems, and the next section is about solving them.

IV

The context budget

Context engineering is deciding what goes in the window, in what form, at what moment. Same task, same model, three harness designs:

The main techniques

Retrieval. Fetch only the relevant passages, by keyword search, semantic search, or both. Agentic search. Let the model grep and open files itself, the way a lawyer skims an index. Compaction. Summarize older turns when the window gets full. Subagents. Send a helper with its own fresh window to read a long document and report back a short answer. Memory files. Write durable notes to a file the harness loads next session, since the model itself forgets everything.

VI

Where LangChain fits

Harness, orchestration, framework: these words overlap because they describe the same pile at different heights. The harness is the whole working system. A framework like LangChain is a box of prebuilt parts you can build a harness from. Orchestration is the part of the harness that runs the steps and the loop. LangGraph is LangChain's orchestration layer.

What to tell a client about frameworks

Frameworks speed up the first prototype and give you many connectors. They also add layers of abstraction that can make it harder to see exactly what the model was sent, which is the first thing you need when debugging. Many experienced teams use the plain model API or a lab's agent SDK for that reason. Neither choice is wrong. What matters is that someone on the team can always answer: what exactly went into the context window, and why?

VII

Tools and MCP

The model never touches a system. It writes a request in a fixed format, and the harness decides whether to run it. A tool is just three things the model can read: a name, a description of when to use it, and an input schema.

What the harness tells the model
// a tool definition
{
  "name": "search_matters",
  "description": "Search the document system
    for agreements by counterparty,
    type or date. Returns titles and
    IDs, not full text.",
  "input_schema": {
    "counterparty": "string",
    "doc_type": "NDA | LPA | side letter",
    "after": "date"
  }
}
What the model writes back
// a tool call: just text, until
// the harness chooses to run it
{
  "type": "tool_use",
  "name": "search_matters",
  "input": {
    "counterparty": "Acme Capital",
    "doc_type": "side letter"
  }
}

// harness runs it, appends the
// result, and calls the model again

MCP, the Model Context Protocol, standardizes this plug. A vendor writes one MCP server for their system, and any MCP-capable harness can use it. Think of it as a standard hitch: any wagon, any tool.

VIII

Guarding the camp

Models follow instructions, and they can't reliably tell your instructions from instructions hidden inside a document, email, or web page. That's prompt injection. Simon Willison's lethal trifecta is the simplest way to reason about it. Turn on the capabilities and watch the middle.

Permission tiers

The harness decides what runs on its own and what waits for a person. A sensible default for a fund:

Evals: the surveyor's instruments

Every harness change, whether a new prompt, a new model or a new tool, can fix one thing and quietly break another. An eval set is a fixed list of real tasks with known-good answers, run after every change. It's the only way to know.

X

A fund, drawn

Here is everything above assembled into one realistic design: a research and documents assistant for a hedge fund that keeps data inside its own cloud. The numbered marks are the decisions you, as the advisor, own.

  1. 1
    Where the model runs. Through the fund's own Azure, AWS or Google account under zero-retention terms, or a vendor's enterprise API. This decision drives what compliance will sign.
  2. 2
    Permissions travel with the data. The index stores each document's access list from SharePoint or iManage, and the harness filters by the signed-in analyst on every search. Information barriers are enforced here, not in the prompt.
  3. 3
    What gets logged, and for how long. Prompts, retrieved documents, tool calls and answers, retained to match recordkeeping rules.
  4. 4
    Who owns the eval set. The fund's own experts should write the cases. You design the method and run it.
  5. 5
    What needs a person. Anything that leaves the building or changes a system of record goes through approval.
XI

Words you'll hear

Harness
Everything around the model that makes it useful: instructions, context assembly, tools, the loop, memory, permissions, guardrails, logging. Also called scaffolding.
Orchestration
The part of a harness that sequences steps: which call happens next, in what order, with what branching or retries.
Framework
A library of prebuilt harness parts, such as LangChain or LlamaIndex. Optional.
Agent SDK
A lab's toolkit for building agent harnesses, such as the Claude Agent SDK or OpenAI Agents SDK. It ships the loop, tool handling and context management ready-made.
Workflow
A harness where your code fixes the steps. The model fills in each step.
Agent
A harness where the model chooses the next step, using tools in a loop until it decides the task is done.
Tool / function calling
The model writes a structured request; the harness runs it and returns the result.
MCP
An open standard for connecting tools and data sources to any compatible harness.
RAG
Retrieval-augmented generation. Search for relevant text first, then put it in the context so the model answers from it.
Context engineering
Designing what the model sees on each call. The core craft of harness work.
Fine-tuning
Changing the model's weights with extra training. A different, rarer tool. Most client problems are harness problems.
Evals
Fixed test sets that score a harness, run after every change.
